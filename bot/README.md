# VK-бот для выдачи прокси

Приложение на `@verse-bot/vk` из проекта `verse-bot`. Использует опубликованный пакет `0.1.0`: соседний репозиторий на сервере не требуется. Работает через Long Poll, без входящих портов.

## Запуск на сервере прокси

### Установка через менеджер (рекомендуется)

При `mtproto-manager install` после настройки прокси можно согласиться на установку VK-бота. Для уже установленного менеджера:

```bash
sudo mtproto-manager bot install
```

В интерактивном меню это пункт **17 — VK-бот**. Установщик спрашивает пользователя запуска, каталог (по умолчанию `~/projects/mtproxy-manager-bot` в домашнем каталоге пользователя, вызвавшего `sudo`), токен сообщества, ID сообщества и администраторов. Допустим собственный абсолютный путь или `~/...`, включая пробелы. Выбранному пользователю нужны Git и доступ к Docker. Установщик не меняет группы автоматически.

Пользователь и абсолютный путь сохраняются в `/etc/mtproto-manager-bot.conf`; Git, Compose и запись `.env` выполняются от этого пользователя. Секреты находятся в `<каталог>/bot/.env` с правами `600`; при перенастройке временная резервная копия сохраняется в закрытом каталоге `bot/.deploy/`. Для ранее установленного скриптом бота укажите его существующий каталог и владельца — менеджер зарегистрирует установку.

```bash
sudo mtproto-manager bot configure  # настройка; Enter сохраняет текущие значения
sudo mtproto-manager bot update
sudo mtproto-manager bot status
sudo mtproto-manager bot logs
sudo mtproto-manager bot start      # также stop, restart
sudo mtproto-manager bot uninstall
sudo mtproto-manager update all     # прокси и зарегистрированный бот
```

Настройка пересоздаёт контейнер с новым окружением. При ошибке возвращаются прежний `.env` и прежний образ; для работавшего бота выполняется повторный запуск. Остановленный бот остаётся остановленным. При прерывании настройки резервная копия может остаться в `.deploy/env.previous`: восстановите её в `.env` или сохраните вне установки перед следующей попыткой.

В пункте 12 меню можно выбрать обновление прокси, бота или всего; CLI `update` без аргумента по-прежнему обновляет только образ telego. Для скачивания новой версии самого менеджера: `sudo mtproto-manager self-update` (пункт 18 меню). Обычный `install` из локального файла устанавливает именно этот файл.

При удалении менеджера предлагается удалить и контейнер бота, а затем отдельно — `.env` и volume с привязками. Отказ от удаления данных сохраняет их для повторной установки. Checkout репозитория и регистрация пути сохраняются, чтобы не удалять чужие файлы и резервные копии. Если оставлен сам бот, после удаления конфигурации прокси он не сможет выдавать ссылки. `/etc/mtproto-manager-bot.conf` не включается в экспорт прокси; `.env` и привязки бота резервируются отдельно.

Состояние хранится в `bot/.deploy/state`: `prepared`, `active`, `stopped`, `removed`. Обновление остановленного бота собирает новый образ, но не запускает его. Удалённый бот пропускается при обновлении, включая Actions; для возврата используйте `install` или `configure`. Статус, логи и удаление работают даже без `.env`. Обновление активной установки без настроек завершается ошибкой.

### Compose-проект и переход со старой установки

Новая установка получает собственное имя проекта `mtproxy-manager-bot-<хеш пути>`, которое сохраняется в `bot/.deploy/project`. Разные каталоги изолированы по контейнерам, образам и volume. Не удаляйте `.deploy/` и не копируйте её в другую параллельную установку.

Для прежнего контейнера проект определяется по Docker-лейблам и совпадению рабочего каталога; его существующий volume сохраняется без переноса данных. Если контейнер уже удалён, но остался `bot_bot-data`, необходимо явно выбрать: `BOT_ADOPT_LEGACY=1` для использования прежних привязок либо `BOT_ADOPT_LEGACY=0` для новой независимой установки. Передайте переменную при первом запуске `deploy.sh`, указав тот же `BOT_INSTALL_DIR`, что используется в менеджере. Это исключает автоматическое присвоение чужого volume.

Используйте менеджер или `deploy.sh` для управления. Для ручной команды Compose из `bot/` всегда указывайте `--project-name "$(cat .deploy/project)"`. Имя `bot` в YAML оставлено только для совместимости первого обновления старым установщиком.

### Установка отдельным скриптом

На VPS нужны Git, Docker Engine с Compose и `flock` (util-linux). Запускайте от пользователя, у которого проекты лежат в `~/projects` и есть доступ к Docker, без `sudo` перед скриптом.

После публикации файлов в `main`:

```bash
curl -fsSL https://raw.githubusercontent.com/vdistortion/mtproto-web-proxy-manager/main/bot/deploy.sh -o /tmp/mtproxy-bot-install.sh
bash /tmp/mtproxy-bot-install.sh install
```

Скрипт клонирует репозиторий в `~/projects/mtproxy-manager-bot` и создаст `bot/.env`. Заполните его, затем повторите:

```bash
bash ~/projects/mtproxy-manager-bot/bot/deploy.sh install
```

Обновление без GitHub Actions — одна команда:

```bash
bash ~/projects/mtproxy-manager-bot/bot/deploy.sh update
```

Она получает изменения `main`, обновляет только fast-forward и собирает образ; контейнер пересоздаётся только для активной установки. `.env` и volume с привязками сохраняются. Локальные изменения исходников останавливают обновление. Параллельные запуски блокируются. Каталог и ветку можно переопределить через `BOT_INSTALL_DIR` и `BOT_BRANCH` (указывайте те же значения при обновлении). `BOT_REVISION` позволяет указать полный SHA коммита этой ветки; переход назад или на посторонний коммит отклоняется.

При ошибке сборки работающий контейнер сохраняется. Ошибка запуска новой версии при `update` не вызывает автоматического отката кода; проверьте `mtproto-manager bot logs`. Healthcheck становится успешным после инициализации VK Long Poll, поэтому `--wait` не принимает просто запущенный процесс за готового бота. Это проверка первоначального подключения, а не непрерывный мониторинг доставки сообщений.

### Автоматическое обновление через GitHub Actions

После первой установки добавьте в GitHub Settings → Environments → `production` secrets:

| Secret            | Значение                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------- |
| `VPS_HOST`        | Адрес VPS                                                                                   |
| `VPS_USER`        | SSH-пользователь, установивший бот; необязательно, по умолчанию `root`                      |
| `VPS_PORT`        | SSH-порт, необязательно (22 по умолчанию)                                                   |
| `VPS_SSH_KEY`     | Приватный ключ для входа; публичную часть добавьте в `~/.ssh/authorized_keys` на VPS        |
| `VPS_KNOWN_HOSTS` | Проверенная запись ключа сервера из `known_hosts`; для нестандартного порта — `[host]:port` |

В Settings → Secrets and variables → Actions → **Variables** (уровень репозитория) задайте `ENABLE_BOT_DEPLOY=true`, чтобы включить деплой. Необязательная переменная `BOT_INSTALL_DIR` задаёт абсолютный путь установки на VPS, например `/srv/apps/my-bot`; без неё используется `~/projects/mtproxy-manager-bot` пользователя `VPS_USER`. Используйте того же пользователя и путь, что выбраны в менеджере.

Workflow `Deploy VK bot` запускает тесты при push в `main`, затрагивающем бота, менеджер, тесты или сам workflow; также доступен ручной Run workflow. Отдельного запуска на pull request нет. Деплой выполняется только для `main` и только при включённом `ENABLE_BOT_DEPLOY`. Проверенная версия `deploy.sh` передаётся по SSH и обновляет VPS до конкретного проверенного SHA, а не до более свежего `main`. Устаревший запуск не откатывает новую версию. Для приватного репозитория отдельно настройте на VPS доступ Git к origin; SSH-ключ Actions нужен для входа на VPS, а не для скачивания репозитория.

Токен VK остаётся в `.env` на VPS и не нужен в GitHub Secrets. Если Actions не настроен, пользуйтесь ручной командой обновления выше.

### Настройка VK и ручной запуск из репозитория

1. В сообществе VK включите сообщения и Bot Long Poll API с событием `message_new`. Создайте токен сообщества с доступом к сообщениям.
2. Из корня репозитория:

   ```bash
   cd bot
   cp .env.example .env
   chmod 600 .env
   ```

3. Заполните `.env`: `VK_TOKEN`, положительный числовой `VK_GROUP_ID`, ваш числовой `VK_ADMIN_IDS` (несколько через запятую). `PROXY_CONFIG_DIR` — каталог менеджера, по умолчанию `/etc/mtproto-manager`.
4. Запустите:

   ```bash
    BOT_INSTALL_DIR="$(git rev-parse --show-toplevel)" bash deploy.sh install
    BOT_INSTALL_DIR="$(git rev-parse --show-toplevel)" bash deploy.sh logs
   ```

Каталог конфигурации монтируется целиком только для чтения, чтобы бот видел атомарные замены файлов менеджером. Docker socket не подключается. Контейнер использует root для чтения конфигурации менеджера с правами `700/600`.

Привязки находятся в `bindings.json` в постоянном volume `bot-data` выбранного проекта. Перезапуск и пересборка их сохраняют. `down -v` удаляет привязки. Резервная копия из `bot/`:

```bash
docker compose --project-name "$(cat .deploy/project)" cp bot:/data/bindings.json ./bindings.backup.json
chmod 600 bindings.backup.json
```

Для восстановления остановите бот через менеджер, выполните `docker compose --project-name "$(cat .deploy/project)" cp ./bindings.backup.json bot:/data/bindings.json`, затем запустите через менеджер. Вместе с привязками отдельно сохраняйте `.env`, `.deploy/project`, `.deploy/state` и регистрацию менеджера; резервные копии содержат чувствительные данные.

## Использование

Непривязанным аккаунтам бот не отвечает ни на сообщения, ни на команды. Заранее получите числовой VK ID пользователя отдельно и отправьте боту в личке:

```text
/bind 123456789 alice
```

`alice` должен уже существовать в менеджере и быть активным. Повторный `/bind` заменяет привязку. Пользователь отправляет `/tg` или нажимает «Мои прокси» и получает четыре ссылки: WEB, WEB (dd), MTProxy (ee), MTProxy (dd). `/start` показывает подсказку и клавиатуру.

После привязки пользователь отправляет первое сообщение (например, `/start`) — в ответ появляется клавиатура: «Мои прокси», «О данных», «Отвязать аккаунт». Сам `/bind` не отправляет пользователю уведомление. Администраторы из `VK_ADMIN_IDS` могут пользоваться ботом без собственной привязки.

Несколько VK ID могут быть привязаны к одному имени: `/bind 123456789 alice` и `/bind 987654321 alice`. Каждая связь независима.

### Самостоятельная отвязка и данные

- `/privacy` или «О данных» — какие данные получает и хранит бот, доступ администратора и роль VK как канала передачи сообщений.
- `/unlink` или «Отвязать аккаунт» — запрос на удаление связи с текущим VK ID. Подтверждение: `/unlink confirm` или «Подтвердить отвязку» в течение двух минут. `/cancel` или «Отмена» отменяет запрос. Перезапуск бота или повторная административная привязка отменяет ожидающее подтверждение.
- После подтверждения связь удаляется из постоянного хранилища, клавиатура скрывается, и бот перестаёт отвечать этому аккаунту. Исключение — администраторы, чьи права задаются отдельно в `VK_ADMIN_IDS`. Другие аккаунты того же пользователя продолжают работать. Повторная привязка выполняется администратором.

Отвязка не отзывает уже выданные ссылки и не удаляет переписку в VK или копии данных из резервных копий. Для отключения самих ссылок нужно обратиться к администратору. При восстановлении старой резервной копии привязки также могут восстановиться.

### Административная отвязка

```text
/unbind 123456789
```

Удаляет только привязку VK. Для отключения уже полученных ссылок используйте `sudo mtproto-manager block-user alice`.

Команды работают только в личке. Администраторы определяются исключительно по `VK_ADMIN_IDS`. Конфигурация перечитывается при запросе: удалённые и заблокированные пользователи ссылок не получают. Смена домена/порта отражается сразу. Привязка содержит отпечаток секрета: после пересоздания пользователя или смены секрета нужен повторный `/bind`. Разблокировка с прежним секретом восстанавливает выдачу автоматически.

## Локальный запуск

Нужен Node.js 22.9+ (рекомендуется 24). Код и тесты написаны на TypeScript 7.0.2 со строгой проверкой типов. Укажите доступный каталог конфигурации в `.env`:

```bash
npm ci
npm run typecheck
npm test
npm start
```

Привязки хранятся в `BOT_DATA_DIR` (по умолчанию `./data`). Запускайте один экземпляр на токен и хранилище. Приложение не журналирует тексты сообщений, токены и ссылки. Ошибки чтения не сбрасывают привязки.

`npm run build` компилирует приложение и тесты в `dist/`; `npm test` сначала выполняет эту сборку. После изменений исходников пересоберите проект перед `npm start`. В Docker сборка выполняется отдельным этапом, в итоговый образ попадают только скомпилированное приложение и runtime-зависимости. Workflow проверяет компиляцию вместе с тестами.
